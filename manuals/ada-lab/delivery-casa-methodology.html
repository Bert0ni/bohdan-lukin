CASA Delivery Methodology (working draft)

This is our interpretation of how a CASA engagement runs. The authoritative method is ADA's Evaluation Methodology + CASA requirements documents — reconcile this file against them once obtained, and keep it a controlled document inside the ISO/IEC 17025 QMS. [VERIFY] everything marked below.

Inputs#

  • Target application + API scope; for AL2 also deployment infrastructure and user-data storage locations.
  • The applicable CASA requirement set (OWASP ASVS-derived; [VERIFY] version/count).
  • Any pre-existing certifications (SOC 2 / ISO 27001) the client wants mapped to CASA requirements.
  • Access: source/scan access, test environment, credentials as needed per assurance level.

Assurance-level workflows#

AL1 — lab tested / lab verified (evidence-led)#

  1. Client (or lab) runs the required automated scans (SAST/DAST/SCA) producing evidence per test case.
  2. Lab reviews and validates the evidence against each applicable CASA requirement.
  3. Lab resolves gaps / requests remediation evidence.
  4. Lab issues the Letter of Validation when all applicable requirements pass.

AL2 — comprehensive (lab-executed)#

  1. Lab performs active testing of the application and its deployment infrastructure and data storage — i.e. a structured pentest mapped to the CASA/ASVS control set.
  2. Lab validates automated + manual findings against every applicable requirement.
  3. Remediation loop; re-test.
  4. Letter of Validation on full pass.

The ASVS-mapped assessment core#

For each applicable requirement (ASVS category):

1Determine applicability to this appapplicability note
2Collect evidence (scan output, config, manual test, mapped cert)evidence artifact ID
3Verify against the requirement's pass criteriapass/fail + rationale
4Decision (conform / nonconform) with traceabilitydecision record
5On nonconform → remediation request → re-verifycorrective-action log

ASVS categories to cover (v5.0 structure — [VERIFY] current CASA subset): encoding/output, validation & sanitization, authentication, session management, access control, cryptography, error handling & logging, data protection, communications/TLS, configuration, business logic, API/web-service, and others per the current standard.

Decision rule & deliverable#

  • Pass: all applicable CASA requirements conform → Letter of Validation (≈12-month validity → annual revalidation).
  • Record everything for traceability: ISO/IEC 17025 requires defensible, reproducible decisions and retained evidence.

QMS integration (non-negotiable)#

  • This method is a controlled document (versioned, change-controlled).
  • Only authorized, competency-recorded assessors may execute it.
  • Each engagement generates records (evidence, decisions, reviews) that feed both the client deliverable and ISO/IEC 17025 auditability.
  • Impartiality: no assessor may validate an app they built/consulted on.

Reuse of existing capability#

Our web/API pentest playbooks map directly onto AL2 active testing; our reporting discipline (confirmed vs. static-only findings, severity calibration, coverage statements) transfers to the evidence/decision records. The build is productization under a QMS, not new research. See toolchain-and-automation.md.
